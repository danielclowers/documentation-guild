# Deployment setup

The hosted preview uses GitHub Pages for the frontend, Clerk development authentication, and the Cloudflare `documentation-guild-preview` Worker and D1 database. [Live welcome screen](https://danielclowers.github.io/documentation-guild/)

## Verify a Clerk development instance

1. In **User & authentication**, enable username and password. Disable email, phone, and social sign-in for this guild. Set public sign-up to restricted. The Worker creates users through the Backend API and checks active D1 membership on every protected route. [Clerk user creation](https://clerk.com/docs/reference/backend/user/create-user) · [Clerk authentication options](https://clerk.com/docs/guides/configure/auth-strategies/sign-up-sign-in-options)
2. In **Sessions**, add `{"aud":"documentation-guild-api"}` to the custom claims on the standard session token. The Worker verifies the token signature, issuer, audience, expiry, and authorized origin. [Clerk session claims](https://clerk.com/docs/guides/sessions/customize-session-tokens)
3. Copy `apps/api/.dev.vars.example` to `apps/api/.dev.vars` and fill in the Clerk development secret and exact Frontend API issuer, including `https://`. Copy `apps/web/.env.example` to `apps/web/.env.local` and set the corresponding publishable key. Use `http://localhost:5173/documentation-guild/` for the frontend so the browser origin matches the local Worker allowlist.
4. Apply migrations with `pnpm --filter @guild/api migrate:local`. Create a username/password admin in the Clerk development instance. With `CLERK_SECRET_KEY` set in your shell environment, run `pnpm --filter @guild/api bootstrap:admin --local user_ID` to link that Clerk user to the local guild. The command checks the user in Clerk before writing the first admin row and can safely be run again for the same user.
5. Run `pnpm dev:api` and `pnpm dev` in separate terminals. Sign in as the admin, create a one-use invitation and redeem it in a separate browser profile with a disposable username and password. Verify that the new member can sign in, that the same link cannot be redeemed twice, and that a valid Clerk account without membership cannot use the guild API. Check suspension, reinstatement and recovery before inviting coworkers.

## Cloudflare

Provision a staging Worker and D1 database. Use an explicit deployment configuration with its real database ID for `DB`, an `AUTH_RATE_LIMIT` binding, a `GUILD_ROOM` binding for `GuildRoom`, and the intended web URL and exact origin allowlist. Include the `hall-v1` SQLite Durable Object migration and keep its tag on subsequent deploys. Keep `CLERK_ISSUER` and `CLERK_AUDIENCE` consistent with Clerk. Set `CLERK_SECRET_KEY` through the Worker secret store. Optionally set the Clerk JWT public key as `CLERK_JWT_KEY` for offline verification. Without it the Worker resolves signing keys through Clerk. Apply migrations to that explicitly selected environment and verify `/health` before wiring it to the frontend. The checked-in Wrangler configuration targets local D1. [Cloudflare local bindings](https://developers.cloudflare.com/workers/local-development/bindings-per-env/) · [Workers rate limiter](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)

## GitHub Pages

The repository is `danielclowers/documentation-guild`. GitHub Actions builds and publishes from `main` with Vite's `/documentation-guild/` base path. Set repository Actions variables `VITE_API_URL` and `VITE_CLERK_PUBLISHABLE_KEY` only when the Worker and corresponding Clerk instance are ready. These are public build inputs. The static build derives its Content Security Policy from the configured API and Clerk frontend origins. Validate the policy in the Clerk staging sign-in test. If attaching a custom Pages domain, update the Vite base path, the Worker `WEB_URL` and origin allowlist, and the Clerk domain settings together. Clerk production requires a domain you control for DNS. [Clerk production deployment](https://clerk.com/docs/guides/development/deployment/production) · [GitHub Pages workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)
